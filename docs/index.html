npm audit for agentic payment SDKs.

agent-audit finds known-vulnerable versions of x402 and related agent-payment packages in your lockfile, including the vulnerabilities that have no published advisory, which npm audit therefore reports as clean.

$ npx agent-audit

The problem

In October 2026 the security firm V12 published research on x402 reporting 25 vulnerabilities, 3 critical and 13 high, disclosed on 12 August 2026 and fixed by 20 August. The three criticals were:

  1. Solana payment bypass. The TypeScript Solana facilitator accepted a token approval (ApproveChecked) as a TransferChecked payment. An approval moving zero tokens was accepted as payment: the resource was delivered and nothing was paid.
  2. No default spending limit. The default client took the first payment option a server offered, with no budget. A hostile API could request the agent wallet's entire balance.
  3. SIWx origin binding. The client signed Sign-In-With-X messages without checking that the named domain matched the host contacted, allowing session takeover by relay.

All three were fixed in 2.23.0. None of them received a security advisory. Queried against OSV.dev on 20 Nov 2026, @x402/core, @x402/fetch, @x402/axios and @x402/extensions have no advisories at all.

There is a second case. GHSA-5cgh-j82v-jvrj is listed on the x402 repository's own advisories page (published 18 Nov 2026), but it returns 404 from GitHub's global advisory API and nothing from OSV. It is a repository-level advisory that never propagated to the databases npm audit reads.

This is not a criticism of the x402 maintainers, who ship fixes quickly. It is a gap in how security information reaches the people running the code.

No fix available: GHSA-5cgh-j82v-jvrj

The TypeScript, Go and Python batch-settlement voucher verifiers accept ECDSA signatures that the on-chain x402BatchSettlement contract rejects (high-s, v = 0/1). The voucher verifies, the resource is served, and the later claim reverts. Severity Moderate, CVSS 3.1 5.4, CWE-347, no CVE.

It affects @x402/evm >= 2.12.0, <= 2.31.0. Patched: None. 2.31.0 is the latest release on npm (published 2026-11-12), so a fully up-to-date install is still vulnerable. npm audit cannot see it.

The provenance rule

A security tool that invents findings is worse than no tool. Every entry declares where its facts came from, and the report shows it.

  • source: "advisory": mirrored from a published GHSA/OSV record. Ranges are upstream's.
  • source: "derived": reconstructed from published research, changelogs or commit history because no advisory exists. It must carry a provenance field explaining how the range was established, and a confidence rating: high, medium or low.

The CLI prints the confidence on any entry that is not high, and a test enforces that every derived entry documents its provenance. The goal is for this database to become unnecessary: entries should be submitted upstream, and once accepted, npm audit starts catching them.

Usage

npx agent-audit                          # scan the current directory
agent-audit ./my-agent               # scan a specific project
agent-audit --role client            # only issues affecting payment clients
agent-audit --chain evm              # only issues affecting this chain: evm or solana
agent-audit --summary                # one line per finding
agent-audit --min-severity critical  # only the worst
agent-audit --only-hidden            # only what npm audit cannot see
agent-audit --json                   # machine-readable output

Supports package-lock.json, pnpm-lock.yaml, yarn.lock (classic and Berry) and bun.lock. Requires Node 20+. Exit code 0 for no findings, 1 for findings, 2 for an error, so it drops into CI as-is:

- run: npx agent-audit --min-severity high

Limitations

Stated plainly, because a security tool should not oversell itself.

  • npm only. The same vulnerabilities affect the Python and Go x402 SDKs. Not yet covered.
  • Version matching, not code analysis. If you patched a vulnerability yourself without upgrading, or call a vulnerable API in a way that is not exploitable, it will still flag you.
  • The database is small and hand-curated. It covers what has been published about x402.
